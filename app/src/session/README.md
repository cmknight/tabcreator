# session/ — one store per aggregate plus analysis.ts, instance-lock.ts (sole owner of Web Locks and BroadcastChannel) and app-reload.ts (spine AD-2, AD-3); may import model/, storage/, engine/ and audio/.

recording-session.ts composes its input derivations through input-derivation.ts: level-watch.ts (level warning), input-quality-watch.ts (input quality warning) and tuner-watch.ts (Tuner reading and ticks); none imports another or the store.

recording-recovery.ts is a module of recording-session.ts (story 3.11): the start-up recovery scan, Open and Discard of unfinished takes; the store composes it and publishes its list as `recovered`.

take-lifecycle.ts is a module of recording-session.ts: the take in progress and the recording state machine (start, count-in, chunks, length limits, failure stops, the save). take-save.ts holds what recording and recovery share: `MIN_TAKE_MS` and its one test `isTooShort`, the clip counter and the save step. The store's `isBusy()` is the one busy answer for its `beforeunload` guard; app-reload.ts's `isAppBusy()` (story 5.7) adds `analysis.isAnalysing()` and is the one busy answer for every app reload (Settings' and the Tab screen's Reload, and the update toast later). `beforeunload` does not ask while analysing: an analysis interrupted by a reload starts again when its Tab opens.

instance-lock.ts gates the app on the Web Lock and hands it over (story 3.10); after a steal the new holder's recovery scan waits for the old holder's `released` message (story 5.3), with a 30 s fallback.

analysis.ts runs a take's analysis (story 5.6): PCM → engine analyze → mapFrets → one `commitAnalysis`, then the raw file is deleted. Runs live in a module-level registry keyed by take id, so a run outlives the session that started it; `isAnalysing()` feeds app-reload.ts's busy check. Its only caller is take-session.ts. The PCM source (ticket 12, AD-15): the raw file; when `readRaw` rejects `audio-missing`, the compressed audio decoded by `audio/decode.ts` at the take's recorded rate (`take.sampleRate`, not the file's native rate: `decodeAudioData` resamples to it), and the engine gets the decoded buffer's rate; with neither (no raw file, and no compressed file or `audioMime` null) the run rejects `audio-missing` (Analysis failed). Decoded audio is never written back and the raw file never recreated; the post-commit `deleteRaw` is skipped for a decoded take. Takes saved by failure stops (mic-lost, storage-full, instance-lost, recovered) are `recorded` like any other and analyse when their Tab opens. Story 5.7: `cancel` settles a run at once with `analysis-cancelled` (the engine worker restarts); a `storage-full` commit keeps the built result in memory as a pending commit (not busy) for `retryCommit`, dropped when the take is deleted or analysed again. Dev builds hold every analysis with `?holdAnalysis` (e2e tests that read a stopped take's raw file or `recorded` status), delay each engine analyze with `?slowAnalysis=<ms>`, and force failures with `window.__analysisFailHook` (`analysis-failed`) and `window.__commitStorageFullHook` (`storage-full` on commit); production builds tree-shake all of them. Story "Analysis settings and re-analysis" (US-4.6): `reanalyse(take, onProgress)` reads the PCM the same way, runs the engine with the take's current settings, trim and count-in skip (progress 0–0.9), and returns the result, the engine version and whether the raw file was read; it commits nothing. It is cancelled by `cancel(takeId)`, counts in `isAnalysing()`, and is cancelled when its take is deleted.

Dev hooks: the readers and state behind every dev-only e2e hook (`__recordingClock`, `?maxTakeMs`/`?warnLeadMs`, the analysis hooks above, `__instanceTest`, `__encodePcmFailHook`; storage/'s `__storageFullHook` and ui/'s `__playbackTrace` too) live in `src/dev/hooks/`. Production modules import them statically and call them only inside `import.meta.env.DEV`, so production builds tree-shake them; the CI dist grep checks.

take-session.ts is the Tab screen's store, one per open take (story 5.6): it loads the take and tab, calls `ensureAnalysed` for a `recorded` take and publishes progress, then the committed take and tab; it handles storage events per AD-5. `dispose()` detaches without cancelling the analysis. Story 5.7: `cancel()`, `analyse()` (Analyse and Retry) and `retryCommit()`; a cancelled run stays cancelled for the session, and a new session analyses a `recorded` take again. Story "Tab screen, reflow and selection": `selectedNoteId` with `select`/`selectNext`/`selectPrev` (played order, kept by note id, cleared when the note is gone) and `rename(title)` (`patchTake` as `take-session`, published locally); `setActiveTakeSession`/`activeTakeSession` hold the mounted Tab screen's session for the ←/→/Esc shortcuts. Story "Flags, warnings and bar lines on screen": `selectNextFlagged(from?)` (Next to check, `N`: the next low-confidence note in played order, wrapping). `lastFocusedNoteId` (set by `focusNote`, cleared when the note is gone) is the one record of the focused note: the arrows, `N` and Next to check start from it with nothing selected, and it holds the tab area's tab stop. The UI reads it through `ui/use-take-session.ts`. Story "Change a fret and undo it" (spine AD-4, AD-16): the edit core. `apply(command)` runs the two-phase commands of `model/edit-history.ts` one at a time per take (a promise queue that undo and redo join): it plans against the current Tab revision, maps each planned request to `engineClient.mapFrets`, drops a result whose revision went stale and plans again, and publishes the reduced Tab as one undo step (at most 200, in memory only; reset when a take loads or an analysis replaces the tab). An engine error drops the command and emits a `failed` edit event. `setFret`, `typeDigit` (a second digit on the same note within 400 ms makes one number and merges into the first's step; the clock is injectable), `undo`/`redo` (the selection follows the step's note), `canUndo`/`canRedo`. The edited Tab is saved with a 300 ms debounced `putTab`; `flush()` saves at once, on dispose (not awaited) and on `pagehide` / `visibilitychange` → hidden while active. A `storage-full` save keeps the Tab and sets the snapshot's `saveFailed` (the screen's banner Retry calls `retrySave`); the next successful save clears it; other save errors are logged and retried on the next flush. On `take-deleted` the pending save and queued commands are dropped. `hasUnsavedEdits()` (a save pending or in flight, or a failed one while its screen is open) feeds app-reload.ts's `isAppBusy()`. Edit outcomes go to `onEditEvent` listeners; the Tab screen words and announces them (this layer may not import `ui/`). Dev builds force `storage-full` on every `putTab` with `window.__putTabStorageFullHook`. Story "String moves, delete, insert and confirm": `moveString(noteId, string)` and `moveStringBy(±1)` (↑/↓: the next thinner or thicker string that plays the pitch, via `model/edit-history.ts` `playablePositions`), `deleteSelected()`, `insert()` (after the selection, or before the first note with none; the new note's id comes from the injectable `newId` dep, default `crypto.randomUUID`, and a digit typed before the insert lands sets its fret) and `confirm(noteId)` run through `apply`. A command's `selectAfter` sets the selection once it applies (a delete: the next note in played order, else the previous; an insert: the new note). Commands apply only while the tab is shown; undo and redo also work with no notes left (No notes found) while there is history. A delete's edit event carries the deleted note's string and fret; a command that changes nothing (confirming a confirmed note) emits no event, except a set fret. Story "Analysis settings and re-analysis" (US-4.6, AD-4): `setSettings(patch)` clamps (`model/analysis-settings.ts`) and saves `settings` with `patchTake` at once (published locally; no undo step; a failed write reverts to the stored settings). `reanalyse()` queues like a command (refused with `audio-missing` when the take has neither compressed audio nor a raw file, `hasAudio`; `hasRaw` is read at load through the `hasRaw` dep): `analysis.reanalyse`, then `model/edit-history.ts` `freshNotes` (new ids, low confidence below c + 0.15), `mergeReanalysis` (fresh notes within 50 ms of a locked note or a `deletedStartMs` entry dropped; locked notes kept unchanged), one `mapFrets` with a lock per locked note (`reanalysisRequest`, `placeReanalysed`: an unlocked note with no position is dropped), one `commitAnalysis` (Tab + `warnings`, `analysisVersion`), then `deleteRaw` when the raw file was read. The snapshot's `reanalysis` carries its progress; meanwhile edits, undo and redo do nothing and the undo and redo labels read null. `cancelReanalysis()` cancels it with nothing changed. A finished re-analysis pushes one snapshot step (`{kind: 'reanalyse'}`, no target) of `{notes, deletedStartMs, settings, trimStartMs, trimEndMs, warnings, analysisVersion}`; undo and redo of it restore all seven through `commitAnalysis`. Its `before` settings are `analysedSettings` (the take's at load or first analysis, then each re-analysis's or restore's). Pending edit saves are held while a `commitAnalysis` writes the Tab. Outcomes go to `onEditEvent` as `reanalysed`, `reanalyseCancelled` and `reanalyseFailed`. Story "Trim": `trim(startMs, endMs)` and `resetTrim()` queue the same re-analysis run with a trim range in place of the take's (the end stored as null at the duration; the full take is `{0, null}`), committing `trimStartMs`/`trimEndMs` with `analysisVersion` and `warnings` in the one `commitAnalysis` and pushing a snapshot step labelled `{kind: 'trim'}` / `{kind: 'resetTrim'}`; the snapshot's `reanalysis` carries `trim: true` meanwhile, and the outcome is a `trimmed` edit event. The audio file is never written. Notes whose `startMs` lies outside `[trimStartMs, trimEndMs ?? ∞)` are hidden (`model/notes.ts` `visibleNotes`; `shownNotes(snapshot)` here): kept stored with their ids, but not selectable, steppable, flagged for Next to check or counted by `isTabShown`, and left out of the edit commands' phrase re-fit. Every re-analysis (a trim, a reset, or a plain one on a trimmed take) merges only the visible locked notes, keeps the hidden locked ones aside unchanged and out of `mapFrets` (`hiddenLocked`), and drops hidden unlocked ones. A trim or a reset (not a settings re-analysis) first anchors its fresh notes to the existing unlocked notes in the new range (`anchorToExisting`: within 50 ms, nearest first, one-to-one; the existing `startMs`, `endMs` and id are kept, the fresh pitch and confidence taken), so existing notes keep their times; fresh notes outside the range are dropped before anchoring, and an unlocked in-range note the engine did not re-detect is kept unchanged (id, times, string, fret), out of `mapFrets`. `trim(start, end)` clamps to the handle rules itself (`model/trim.ts`: the end in 500 ms..duration, the start in 0..end − 500) and ignores non-finite input. A trim's cancel and failure events carry `trim: true` ("Trim cancelled", "Trim failed — try again").

settings-session.ts holds the engine status (About) and a `prefs` snapshot loaded with `loadPrefs()` (story "Flags, warnings and bar lines on screen"); `setBarLines(on)` writes `prefs.barLines` through `updatePrefs` and publishes. `subscribePrefs` subscribes without asking the engine for its version, so the Tab screen never starts the engine. recording-session.ts keeps its own `updatePrefs` calls for the mic and count-in fields. Story "Analysis settings and re-analysis": the snapshot's `prefs` also carries `analysisDefaults`; `setAnalysisDefaults(patch)` clamps and writes them (the Settings screen's "Defaults for new takes"), which recording-session copies into each new take.

waveform.ts (story "Trim") gives the Trim strip its waveform: `loadPeaks(take, columns)` reads the PCM as analysis does (the raw file, else the compressed audio decoded on the main thread by `audio/decode.ts`; `audio-missing` with neither) and sends it once per take (transferred) to `audio/waveform-worker.ts` (a module worker of its own, not the engine worker, AD-8), which keeps it and answers one `peaks` request per column count (`model/waveform.ts` `reducePeaks`), routed by request id. Peaks are cached per take and column count (8 sets, least recently used dropped); a failed load is not cached. `release(takeId)` (the strip unmounting; a `take-deleted` event) drops the take's PCM in the worker and its peaks. A worker `error` or `messageerror` rejects every pending request and the next request starts a new worker (sending the PCM again). Without `Worker` (jsdom) the same handler runs on the main thread. `ui/` reaches `audio/` only through it.

playback.ts (story "Playback with a following cursor") gives the Tab screen's playback the take's compressed audio (`readTakeAudio`, `audioStore.readCompressed`) and holds the mounted screen's playback controller (`setActivePlayback`/`activePlayback`) for the Space and `P` shortcuts, a sibling of take-session's active-session slot. The playback state itself (the `<audio>` element, speed, the cursor) is UI state in `ui/use-playback.ts` and is never stored.

library-session.ts (story "Library list (tracer)", US-7.1) is the Library screen's store: `{loading, rows, error}`, read with useSyncExternalStore. Its first listener starts it: one `db.listTakes()`, one `db.listTabs()` and one `audioStore.listCompressed()` (with byte sizes), built into rows by `model/library.ts` (`libraryRow`, `sortRows`: newest first by `createdAt`). While it has listeners it follows storage events (AD-5): `take-put` and `tab-put` re-read that take, its tab and its size (`compressedSize`) and replace, insert or remove its row; `take-deleted` removes it; `library-restored` reads everything again. Events that arrive during a full read are applied once it lands; a refresh overtaken by a later one or by a delete is dropped. When the last listener leaves it stops following events, and the next first listener reads the library again (the old rows stay shown meanwhile). A failed full read sets `error` to its AppError code (logged), and the events that arrived during it are still refreshed; the next successful refresh clears `error` and reads the library again. A failed size listing leaves sizes blank until a per-take refresh fills them; the listing itself skips a file that is gone or fails to open rather than failing. With two compressed files for one take, the one matching its `audioMime` gives the size (`model/library.ts` `pickSize`, `compressedSize(id, mime)`). It reads only storage (AD-3). Story "Rename, delete take and delete audio" (6.2) adds its writes, as the `library-session` writer (AD-14): `rename(id, title)` (`model/title.ts` `renamedTitle`: trimmed, at most `TITLE_MAX` code points, empty or unchanged writes nothing; `patchTake` of `title`, shown on the row at once and kept over refreshes until written; when the latest rename fails the row re-reads the stored title), `deleteTake(id)` (`db.deleteTake`: the take, its tab and every audio file, files best-effort; the row goes with `take-deleted`) and `deleteAudio(id)` (only for an analysed take that still has `audioMime`, else nothing: `patchTake` of `audioMime: null` first, then `audioStore.deleteAudio` and `deleteRaw`, best-effort (AD-15); a failed patch removes no file; the row shows "Audio deleted" through `take-put`; files left by a failed removal go in recording-recovery's start-up scan). A failed write is logged and rejects; the Library screen shows a toast. An open Tab session picks up a rename or deleted audio through its `take-put` re-read. A take deleted while no Tab session is open still drops take-session's held storage-full edit (`heldTabs`, cleared by one module-level `take-deleted` listener) and analysis's pending commit (its listener stays subscribed while a commit is pending). Story "Back up the library" (6.5, US-7.3) adds `backUp()`: one backup at a time (a call while one runs does nothing and resolves to null), its progress published as `backup: { progress: 0..1 }` in the snapshot (null when none runs, and again once it ends, success or failure). It calls `storage/backup.ts` `createBackup` (the manifest from `db.listTakes`/`db.listTabs`, the zip built in `storage/backup-worker.ts` from OPFS) and resolves to `{ blob, fileName, takes, missingAudio, unsupportedAudio }`; a progress report after the run ended is dropped; the Library screen downloads the Blob through `ui/platform.ts` (AD-2). A failure is logged and rejects. Story "Restore from a backup" (6.6, US-7.3, Flow 4) adds `readBackup(file)` (storage/restore.ts: the backup worker's `read` unzips it and `validateBackup` checks it in full; nothing is written; resolves to the checked backup with `toImport`/`toSkip` counted against `listTakes`) and `restore(backup)` (after the screen's Confirm: re-reads the existing ids, writes the audio of the new takes with `audioStore.writeCompressed`, then their records with `db.importTakes`, which skips ids present by then; a failed write removes the audio written so far, `deleteAudio`, and writes no record; resolves to `{ imported, skipped }`). `restoring` in the snapshot is true while either runs. A backup and a restore step never overlap: a call while the other (or another of the same) runs does nothing and resolves to null. The list refreshes on `importTakes`' `library-restored`. Failures are logged and reject. Stories 6.3 (search) and 6.7 (storage states) build on its rows.
